# Source and Token Contract

Read before extracting rules and building foundations. Product-specific sources are task inputs, not permanent content in this skill.

## Product reference material

Choose the smallest set that can establish the agreed scope:

| Material | What it can establish | Limitation |
| --- | --- | --- |
| Existing Figma library | IDs, properties, variants, bindings, styles | Appearance alone does not establish structural quality or publication |
| Product documentation and decisions | Component meaning, usage rules, intended behavior | Drafts and recommendations are not approved standards |
| Code, tokens, CSS, Storybook | Values, actual states, APIs, dependencies | Implementation may differ from the intended system |
| Running product | Layout, interactions, responsiveness, content cases | One view does not define every rule |
| Screenshots and exports | Visual checks and examples | Image-derived dimensions are measurements or inferences, not a component contract |

Record the source version, commit, or manifest when available. Do not require a repository for a task based entirely on supplied images. In that case, label reconstructed values and decisions that need confirmation.

Establish precedence from the current request and accepted decisions. When documentation, code, and Figma disagree, show the specific values and their provenance. Do not automatically favor code or existing Figma assets. Resolve a blocking conflict before building dependent elements; other work can proceed.

## Information status

- Observed: confirmed in a specific source.
- New Figma mapping: an alias, style, family, or property name created in this task.
- Recommendation: a proposed product or system change.
- Needs confirmation: missing evidence, a conflict, or an uncertain reading.
- Requires runtime testing: behavior that needs implemented code and a running product.

Documentation generated by another agent also requires provenance checks for material values. Confident wording does not replace evidence. Preserve the existing distinction between drafts and accepted rules.

## Token map

Maintain the following mapping for relevant tokens:

    source / role → Figma name → value or alias → application → code equivalent

An architectural example, not a palette or scale for every product:

    primitive value → semantic role token → component property

Reuse the existing architecture when it fits the product. For a two-tier system, create primitive values before semantic aliases. Add component-level tokens when the existing system or a need for independent changes justifies them; do not create them mechanically for every element.

- A variable stores a value. A text or effect style groups settings; do not replace a complete style with a size variable alone.
- Create only the collections and modes needed. Repeated use of the same value does not automatically imply the same semantic role.
- Repeated roles and shared scales warrant tokens. One-off geometry, icon grids, and intentional exceptions may remain fixed and documented.
- Set scopes according to purpose. Empty scopes on a primitive limit its visibility in pickers; they do not indicate publication status.
- Verify aliases: correct type and target, no cycles, and correct values in every relevant mode.
- Bind appropriate colors, strokes, padding, gaps, radii, and typography to components. Creating Variables alone does not ensure their use.
- Code syntax must point to actual code symbols. For an existing CSS variable, use var(--name). Do not invent a CSS variable to conceal a missing equivalent. A literal remains a documented literal; a proposed name is a proposed mapping.

Report primitive values, aliases, and metrics separately. A large variable count does not imply as many independent design rules.

## Responsiveness and states

Record actual breakpoints, maximum widths, min/max constraints, margins, content-order changes, and content behavior. Desktop/Mobile labels are variant names until tied to concrete rules.

Explain what responds fluidly to resizing and what requires selecting a variant or mode. Do not describe manual Viewport switching as automatic responsiveness.

Preserve actual state combinations and justified variant axes. Do not generate the full Cartesian product of all properties when the product does not support it. Missing loading, disabled, dark, or RTL states are gaps or scope limitations; their absence alone does not authorize designing them.
